# Codex adapter

Projects the WellForge workflow onto [OpenAI Codex](https://developers.openai.com/codex) —
the CLI and the IDE extension, which read the same files. Option (b), like the
[OpenCode](../opencode/README.md) and [Copilot](../copilot/README.md) adapters: the Claude
Code plugin (`wellforge-plugin/`) stays the source of truth and this **generates**
Codex-native files from it.

Codex is the closest of the three to Claude Code. As of 2026-10 it has parallel custom
subagents, Agent Skills, and lifecycle hooks with the Claude contract (same payload fields,
exit 2 + stderr to block, a `Stop` hook that continues the turn). So the enforcement here is
**the plugin's own hook scripts, unchanged**, not a reimplementation — the thing the other
two adapters could not do.

## Generate

```bash
uv run --with pyyaml python adapters/codex/generate.py --out <project-dir>
```

Re-run it to update; it is idempotent and touches only what it owns. Then, in Codex, once
per project: **trust the project** (project-scoped `.codex/` config, agents and hooks load
only in a trusted project), and **review and trust the hooks with `/hooks`** — Codex skips
a hook until it is trusted, and again whenever its content changes, so a regenerate that
changes a hook asks again.

Writes into `<project-dir>`:

| Output | From | Notes |
|---|---|---|
| `.agents/skills/wf-<cmd>/SKILL.md` | `commands/` | Codex replaced custom prompts with skills, so each command is a skill invoked **by name**: `$wf-spec <feature>`. `agents/openai.yaml` sets `allow_implicit_invocation: false` — `$wf-release` tags and pushes, `$wf-orchestrate` spawns a team; neither may run because a sentence resembled its description. `$ARGUMENTS` becomes "the text after `$wf-x`" |
| `.agents/skills/<name>/` | `skills/` | SKILL.md is the shared format — copied, refs translated, command links repointed |
| `.codex/agents/wf-<agent>.toml` | `agents/` | Codex custom agents: `developer_instructions` = the agent body, `model` + `model_reasoning_effort` from routing × tiers |
| `.codex/config.toml` | `.mcp.json` | `[mcp_servers.*]` inside a `# >>> wellforge` block; your own servers win on a name clash |
| `.codex/hooks.json` + `.codex/wellforge/hooks/` | `hooks/scripts/` | the plugin's scripts behind [`hooks/run-hook.sh`](hooks/run-hook.sh); only entries that run that runner are replaced, yours are kept |
| `.codex/wellforge/{scripts,config}/`, `eval-rubric.yml` | `scripts/`, `config/` | the deterministic layer (`forge-state.py` & co., via [`deterministic.py`](../deterministic.py)) and the evaluator's rubric |
| `AGENTS.md` | (generated) | a short `<!-- wellforge-codex -->` block: workflow, how to invoke, the agents, what the hooks enforce. Appended; the rest of the file is yours |

Refs are translated: `/wellforge:x` → `$wf-x`, `wellforge:<agent>` → `wf-<agent>`.
`.agents/skills/` is shared with every tool that reads the Agent Skills layout, so the
generator records the directories it wrote (`.codex/wellforge/generated-skills.txt`) and
prunes only those.

## Or: the native Codex plugin

The same output, installed once instead of generated into every project:

```bash
codex plugin marketplace add matteocodogno/wellforge --ref plugin-v2.62.1
# install WellForge from that marketplace, then in each project:
$wf-setup            # or: $wf-setup --hooks  (see below)
```

`wellforge-codex-plugin/` is generated by `generate.py --package` and **committed** — a
marketplace installs from git — and listed by
[`.agents/plugins/marketplace.json`](../../.agents/plugins/marketplace.json). CI regenerates
it and fails on any difference, so edit the plugin and regenerate:

```bash
uv run --with pyyaml python adapters/codex/generate.py \
    --package wellforge-codex-plugin --marketplace .agents/plugins/marketplace.json
```

| Piece | Where | Why there |
|---|---|---|
| command skills + skills | the plugin (`skills/`) | a Codex plugin carries skills |
| MCP servers | the plugin (`mcp.json`, a portable `type` per server) | likewise |
| hooks | the plugin (`hooks/hooks.json`, `${PLUGIN_ROOT}`) | likewise — see the caveat below |
| agents `.codex/agents/wf-*.toml` | **the project**, via `$wf-setup` | a Codex plugin cannot carry custom agents |
| `$WF` (`.codex/wellforge/`), rubric, `AGENTS.md` block | **the project**, via `$wf-setup` | a skill cannot resolve the plugin's install path the way a hook can; in the project `$WF` resolves exactly as in the per-project adapter, so the command skills are the same bytes in both |

`$wf-setup` is the plugin's **onboarding skill** (hand-written source:
[`plugin/wf-setup/`](plugin/wf-setup/)). It is idempotent, writes only WellForge-owned files
plus the marked `AGENTS.md` block, records the release in `.codex/wellforge/VERSION`, and is
re-run after every plugin update — the plugin's SessionStart hook says so when a project is
behind, or was never set up.

**Hooks caveat.** Codex documents plugin hooks for *manually installed desktop plugins*
only. Where they do not run (`/hooks` does not list them), `$wf-setup --hooks` installs the
same hooks into the project (`.codex/hooks.json` + `.codex/wellforge/hooks/`). When both
are present the plugin's runner **steps aside**, so no guard runs twice and no subagent is
traced twice; the project's copy is then refreshed on every `$wf-setup`.

Don't mix the two modes in one project: the per-project generator also writes
`.agents/skills/`, and Codex would list every WellForge skill twice (`$wf-setup` warns).

## Provider / model routing

`routing(agent → tier) × tiers(codex → openai → tier → model)` in `wellforge-plugin/config/`,
plus `reasoning_effort.codex` (frontier `high`, mid `medium`). A custom agent cannot override
`model_provider` — it inherits the session's — so `openai` is the only provider. The model
ids are a **template**: confirm them with `/model` in your Codex before relying on them.

## Support tier (honest)

The workflow, the agents, the skills, MCP **and** local enforcement. What differs:

| Claude Code hook | Codex | Ported |
|---|---|---|
| pre-bash-guard | `PreToolUse` `Bash` (also matches unified exec) | ✓ unchanged script |
| pre-file-guard (secret files) | `PreToolUse` `apply_patch` | ~ the **write** half: the runner extracts every path a patch adds, updates, moves or deletes and runs the guard once per path. Codex has no Read tool — it reads through the shell — so the **read** half is pre-bash-guard's command-text check, as on OpenCode; a read through an MCP tool is not covered |
| post-lint | `PostToolUse` `apply_patch` | ✓ unchanged script, per patched file |
| post-spec-guard (lifecycle gates) | `PostToolUse` `apply_patch` | ✓ unchanged — the `status: done` gate and the raise-only `rigor:` rule are **mechanism** here, as on Claude Code (not prompt promises, as on Copilot/OpenCode) |
| stop-verify (spec drift, compile) | `Stop` | ✓ unchanged; exit 2 makes Codex continue the turn with the reason, `stop_hook_active` stops the loop |
| session-start | `SessionStart` | ✓ plain stdout becomes developer context, as on Claude Code |
| subagent-decisions-guard (`DECISIONS:` in dev/devops reports) | `SubagentStop` (`^wf-` agents) | ~ unchanged script; it reads `last_assistant_message` or the Claude transcript shape, and fails open when neither is there — so on Codex it enforces only if the payload carries the final message (unverified) |
| trace-subagent (observability) | `SubagentStop` (`^wf-` agents) | ~ the event, agent type and id are recorded; token usage is best-effort — the script reads the Claude transcript shape and Codex's rollout format is different, so expect empty token fields until that is verified |
| notify | — | ✗ Codex's own `notify` setting (an external program on turn completion) is user config, not a hook; configure it in `~/.codex/config.toml` if wanted |
| pre-compact-backup | — | ✗ not wired: it writes under `.claude/`, which means nothing here (lower value) |

**Orchestration.** Codex spawns custom agents in parallel and waits for all of them. What it
does not have is per-agent worktree isolation — subagents share the checkout, and a custom
agent cannot override the sandbox. So `$wf-implement` / `$wf-orchestrate` take the
worktree-isolation **Fallback**: a batch of ≥2 implementation agents runs **sequentially**.
Read-only stages (security review, eval) may still fan out.

**Tool allowlists** are not representable: a Codex custom agent inherits the session's
sandbox and approval policy, and reads through the shell, so disabling the shell would
blind it. The Claude `tools:` list becomes a "Tool scope" paragraph at the top of the
agent's instructions (read-only agents told to use the shell only to read). The CI gates
and the hooks above are the enforcement; that paragraph is a promise.

## Coverage (machine-checked)

`adapters/smoke-test.py --adapter codex` asserts every plugin command, agent and skill has a
counterpart here, and (assertion f) that the TOML parses and every hook wired in
`hooks.json` runs a script that exists and is valid bash. A deliberate gap is legitimate —
an **undeclared** one is the bug, so the exceptions live in this block and nowhere else.

```yaml wellforge-adapter-coverage
intentionally_absent:
  commands: []
  agents: []
  skills: []
```

The runner's payload translation has its own matrix:
`scripts/tests/codex-hooks.test.py` drives `run-hook.sh` with Codex-shaped payloads against
the real plugin scripts.
